## 業務ルールの仮案

- **自動取消はしない。** 未払い注文は注意表示だけを出す。調理開始後の来場者取消は不可で、スタッフが対応する。
- **未払いのまま受け渡しはできない。** 例外は会計責任者が理由を入力したときだけで、監査ログに残る。
- **取消と返金は別の操作。** 支払済み注文の取消は会計責任者だけができる。返金累計は入金額を超えられない（DBのトリガーでも保証）。
- **数量の途中分割はしない。** 支払前なら明細単位で取消できる。支払後は返金で対応する。
- **複数人予約は1人1枚の入場チケットにする。** 当日受付もチケットを作るので、人数の数え方がそろう。チェックインでは席数を増やさない。
- **入場後の取消・部分取消・遅刻時の席開放は未実装。** 入場済みチケットがある予約は取消できない。管理者は入場を取り消せる。
- **URLを紛失したとき**は、受付が本人確認をして（方法は運用で決める）URLを再発行する。旧URL・旧入場QR・旧クーポンQRはすべて無効になる。
- **クーポンの自動発券**は、上映終了後に入場記録のあるチケットを対象に行う。途中退場は検証しない。
  - 一人一枚の設定なら、チケットごとに1枚。
  - 一枚で複数人分の設定なら、予約ごとに入場人数分を1枚。
- **クーポンの計算ルール**
  - 定率は1円未満切捨て。割引は対象金額を超えない。
  - 対象商品が複数あるときの割当順（高い順／安い順）はクーポンごとに設定する。
  - 併用不可が既定。発券時の条件はスナップショットとして固定し、後から定義を変えても発券済みには影響しない。
- **クーポンの復元**
  - 返金時の復元は「全額返金」のときだけ選べる。
  - 単独の利用取消は、全額返金済みか、未払いで取り消された注文に限る（二重割引を防ぐため）。
- **商品の選択肢**は軸（味・サイズなど）と値を管理画面から追加できる。
  - 軸を追加すると全組み合わせを作り直す。価格と販売状態は、それを含む旧組み合わせから引き継ぐ。
  - 履歴にある商品は削除せず無効化する。
- **ブロックはブラウザのCookieとアプリの識別値が単位。** 同一人物の断定はせず、IP単独の恒久ブロックもしない。既存の取引は自動取消しない。
- **シフトの交代**は「申請 → 相手承諾 → 管理者承認」で確定配置を更新する。通知はアプリ・Web内の未読通知のみ。

## 未対応・要確認のまま

- 開催日・試運転日（ダミーでは「今日から3日間」）、正式価格、税込表示。
- 端末の台数・OS・設置場所。
- 欠席申請、出退勤、外部通知（メール・LINEなど）。
- Wallet パスの自動更新サービス。
- 個人情報（予約名）の保存期限。開催後に削除する手順を決めること。
- オフラインでの受付・会計（初期案どおりオンライン前提）。通信断のときの紙運用は `当日運用手順.md` を参照。

## セキュリティ上の設計

- 内部ID（UUID）、公開番号（呼出番号・予約番号・チケット番号）、秘密トークンは分けて持つ。
- 注文URL・予約URLのトークンはランダム256bitで、DBにはハッシュだけを保存する。
- 入場QR・クーポンQRは `APP_SECRET` と内部IDから導出するため、平文を保存せずに再表示できる。
- 現地コードも `APP_SECRET` と時間窓から導出する。一般APIからは取得できず、表示端末の権限が必要。
- GET では取消・入場確定をしない。
- ログに秘密トークンを含むパスを残さない。`Referrer-Policy: no-referrer` を付ける。
- 権限の判定はすべてAPI側で行う。画面の表示切替は利便性のためだけ。
